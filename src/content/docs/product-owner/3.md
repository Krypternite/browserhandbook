# SQL Analytics Interview Learning Pack

## Product Owner / Analytics Interview

**Goal:** Become comfortable enough with SQL to solve practical analytics problems and explain the business meaning of your results.

**Target audience:** Someone transitioning from frontend development into a Product Owner / analytics-oriented role.

**Recommended time:** 10–14 focused hours over one weekend.

---

# 0. How to Use This Pack

Do **not** read this from beginning to end passively.

Use this cycle:

```text
Learn concept
    ↓
Look at example
    ↓
Hide solution
    ↓
Solve problem
    ↓
Explain your reasoning aloud
    ↓
Check solution
    ↓
Understand mistake
```

For every SQL problem, ask yourself:

1. What does one row represent?
2. Which table contains the information?
3. Do I need a JOIN?
4. Could the JOIN create duplicate rows?
5. Do I need filtering?
6. Do I need aggregation?
7. Do I need `DISTINCT`?
8. Do I need a window function?
9. What exactly does the resulting metric mean?

# 2. Understand the Relationships

The central relationships are:

```text
Customers
    |
    | customer_id
    ↓
Orders
    |
    | order_id
    ↓
Order_Items
    |
    | product_id
    ↓
Products
```

And separately:

```text
Customers
    |
    ├── Events
    |
    └── Subscriptions
```

The most important thing to understand:

```text
Customers
1 row = 1 customer

Orders
1 row = 1 order

Order_Items
1 row = 1 item line

Events
1 row = 1 event
```

These grains are **not interchangeable**.

---

# 3. Grain — The Most Important Analytical Concept

Suppose Alice has three orders.

In `customers`:

```text
Alice → one row
```

In `orders`:

```text
Alice → three rows
```

In `order_items`:

```text
Alice's orders → potentially many rows
```

Therefore:

> Whenever you JOIN tables, ask how the number of rows changes.

This single habit prevents many analytical mistakes.

# 4. SQL Execution Mental Model

When you write:

```sql
SELECT ...
FROM ...
WHERE ...
GROUP BY ...
HAVING ...
ORDER BY ...
LIMIT ...
```

think roughly:

```text
FROM
 ↓
JOIN
 ↓
WHERE
 ↓
GROUP BY
 ↓
HAVING
 ↓
SELECT
 ↓
ORDER BY
 ↓
LIMIT
```

This explains:

- why `WHERE` cannot normally contain aggregate conditions
- why `HAVING` exists
- why aliases may behave differently depending on SQL dialect
- why JOINs can affect aggregation

```sql

    COUNT(CASE
        WHEN status = 'Completed' THEN 1

        WHEN status = 'Cancelled' THEN 1
    END) AS cancelled_orders
```


# 9. The LEFT JOIN Trap

Consider:

```sql
SELECT
    c.customer_id,
    COUNT(o.order_id)
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
WHERE o.status = 'Completed'
GROUP BY c.customer_id;
```

This can effectively eliminate customers with no completed order because the `WHERE` condition filters the NULL side.

A safer pattern when you want to preserve all customers is:

```sql
SELECT
    c.customer_id,
    COUNT(o.order_id) AS completed_orders
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
    AND o.status = 'Completed'
GROUP BY c.customer_id;
```

### Important interview concept

The placement of conditions matters.

Compare:

```text
condition in ON
```

versus:

```text
condition in WHERE
```

especially with `LEFT JOIN`.

# 10. The Double-Counting Trap

This is extremely important.

Imagine:

```text
Orders
order_id | amount
101      | 500
```

and:

```text
Order_Items
order_id | product
101      | Mouse
101      | Keyboard
```

After JOIN:

```text
101 | 500 | Mouse
101 | 500 | Keyboard
```

If you do:

```sql
SUM(amount)
```

you may calculate:

```text
1000
```

instead of:

```text
500
```

### Interview response

If asked why a metric suddenly doubled:

> "I'd first check whether a one-to-many join changed the grain and caused the measure to be repeated across child rows."

That is an excellent answer.

# 11. Product Revenue

Use `order_items` and `products`.

The product revenue can be derived as:

```text
price × quantity
```

Query:

```sql
SELECT
    p.product_name,
    SUM(p.price * oi.quantity) AS product_revenue
FROM order_items oi
JOIN products p
    ON oi.product_id = p.product_id
JOIN orders o
    ON oi.order_id = o.order_id
WHERE o.status = 'Completed'
GROUP BY p.product_name;
```

### Important analytical issue

This assumes the current `products.price` represents the transaction price.

In a real system, you would want to know whether the order item stores the **actual price at purchase time**.

Why?

Because product prices can change.

This is exactly the sort of business/data-quality question a PO should ask.

```sql
    SELECT
        customer_id,

    FROM orders
    WHERE status = 'Completed'

FROM customer_revenue

```

### Why use a CTE?

It separates:

```text
calculation
```

from:

```text
filtering
```

and makes complicated queries easier to reason about.

# 13. Subquery Practice

Find customers whose revenue is greater than the average customer revenue.

```sql
SELECT
    customer_id,
    SUM(amount) AS revenue
FROM orders
WHERE status = 'Completed'
GROUP BY customer_id
HAVING SUM(amount) > (
    SELECT AVG(customer_revenue)
    FROM (
        SELECT
            customer_id,
            SUM(amount) AS customer_revenue
        FROM orders
        WHERE status = 'Completed'
        GROUP BY customer_id
    ) x
);
```

This is harder.

Don't worry if it feels uncomfortable.

For the interview, understanding **what the query is doing** is more important than memorizing this syntax.

# 14. Window Functions

## Q22 — Number Orders Per Customer

```sql
SELECT
    customer_id,
    order_id,
    order_date,

    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY order_date DESC
    ) AS order_number

FROM orders;
```

The newest order for each customer gets:

```text
1
```

---

# 15. Latest Order Per Customer

```sql
WITH ranked_orders AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY order_date DESC
        ) AS rn
    FROM orders
)

SELECT *
FROM ranked_orders
WHERE rn = 1;
```

### This is a very important pattern.

Memorize the **idea**, not the exact text:

```text
PARTITION
→ group logically

ORDER BY
→ decide what is first

ROW_NUMBER
→ assign position

WHERE rn = 1
→ keep the first
```

```text
   ↓

   ↓
```

# 19. Month-over-Month Growth

Conceptually:

```text
(current - previous) / previous
```

SQL pattern:

```sql
WITH monthly_revenue AS (
    SELECT
        DATE_TRUNC('month', order_date) AS month,
        SUM(amount) AS revenue
    FROM orders
    WHERE status = 'Completed'
    GROUP BY DATE_TRUNC('month', order_date)
),

with_previous AS (
    SELECT
        month,
        revenue,
        LAG(revenue) OVER (
            ORDER BY month
        ) AS previous_revenue
    FROM monthly_revenue
)

SELECT
    month,
    revenue,
    previous_revenue,
    (revenue - previous_revenue)
        / NULLIF(previous_revenue, 0) AS growth_rate
FROM with_previous;
```

### Important

Date functions differ between:

- PostgreSQL
- MySQL
- SQL Server
- Oracle

Know the **concept** even if syntax varies.

# 21.1 DAU

DAU = Daily Active Users.

A common definition:

> Unique users performing a defined meaningful action on a particular day.

SQL pattern:

```sql
SELECT
    event_date,
    COUNT(DISTINCT customer_id) AS dau
FROM events
GROUP BY event_date
ORDER BY event_date;
```

### Product Owner question

What counts as "active"?

Don't assume.

A login may not be enough.

You might define active as:

```text
purchase
feature usage
content creation
transaction
```

depending on the product.

---

# 21.2 MAU

Monthly Active Users:

```sql
SELECT
    DATE_TRUNC('month', event_date) AS month,
    COUNT(DISTINCT customer_id) AS mau
FROM events
GROUP BY DATE_TRUNC('month', event_date);
```

Suppose Feature A is represented by:

```sql
SELECT
```

```text
Adoption = feature_users / eligible_users
```

# 21.5 Conversion Rate

Suppose:

```text
Signup → Purchase
```

A basic approach:

```sql
SELECT
    COUNT(DISTINCT CASE
        WHEN event_type = 'Signup'
        THEN customer_id
    END) AS signups,

    COUNT(DISTINCT CASE
        WHEN event_type = 'Purchase'
        THEN customer_id
    END) AS purchasers

FROM events;
```

Then:

```text
Conversion =
purchasers / signups
```

### But there's a problem.

A user might have:

```text
Signup
Purchase
```

months apart.

For a proper funnel, you may need to establish:

> Did the purchase occur after signup within the defined window?

This is where analytics becomes more sophisticated.

# 22. Funnel Analysis

A typical funnel:

```text
Signup
  ↓
Feature Usage
  ↓
Purchase
```

For each stage, calculate unique users.

Example:

```sql
SELECT
    COUNT(DISTINCT CASE
        WHEN event_type = 'Signup'
        THEN customer_id
    END) AS signup_users,

    COUNT(DISTINCT CASE
        WHEN event_type = 'Feature_A'
        THEN customer_id
    END) AS feature_users,

    COUNT(DISTINCT CASE
        WHEN event_type = 'Purchase'
        THEN customer_id
    END) AS purchasers
FROM events;
```

Then calculate:

```text
Signup → Feature
Feature → Purchase
Signup → Purchase
```

### Product thinking

Don't just report:

> "Conversion is 30%."

Say:

> "The biggest drop occurs between onboarding and feature adoption, so I would investigate that stage first."

# 23. Retention

Retention asks:

> Do users come back after their initial activity?

For example:

```text
January cohort
100 users

February active
30 users

Retention = 30%
```

A proper retention analysis generally requires:

1. cohort date
2. return activity date
3. defined retention window

---

# 24. Cohort Thinking

Suppose users sign up in:

```text
January
February
March
```

You don't want to compare all users together.

Instead:

```text
January cohort
February cohort
March cohort
```

Then measure each cohort's subsequent activity.

### Why?

Because a product's overall retention can change simply because the mix of new users changed.

# 25. Churn

Do not define churn yourself without clarification.

A strong interview response:

> "I'd first clarify the business definition of churn. For example, if churn means no completed transaction for 90 consecutive days, I'd identify customers whose latest qualifying activity is more than 90 days ago."

That answer demonstrates:

- product thinking
- analytical thinking
- awareness of business definitions

# 26. Average Order Value

AOV:

```text
Total Revenue
-------------
Number of Orders
```

SQL:

```sql
SELECT
    SUM(amount) / COUNT(*) AS aov
FROM orders
WHERE status = 'Completed';
```

Better:

```sql
SELECT
    AVG(amount) AS aov
FROM orders
WHERE status = 'Completed';
```

### Why might these differ?

NULLs, unusual data, or different definitions of what counts as an order.

Always understand the business definition.

```text
Revenue
```

Then investigate each component.

# 30. Product Analytics Case

### Interviewer

> "Feature adoption increased, but revenue decreased. What would you investigate?"

A strong answer:

> "I wouldn't assume that higher feature adoption caused revenue to decline. I'd first validate the metric definitions and timeframe. Then I'd segment users who adopted the feature versus those who didn't and compare conversion, order frequency, AOV, and retention. # 32. SQL Interview Trap Questions

## Trap 1

What's the difference?

```sql
COUNT(*)
```

vs

```sql
COUNT(customer_id)
```

Answer:

`COUNT(*)` counts rows.

`COUNT(customer_id)` counts non-NULL customer IDs.

---

## Trap 2

What's the difference?

```sql
COUNT(customer_id)
```

vs

```sql
COUNT(DISTINCT customer_id)
```

Answer:

The second counts unique customers.

---

## Trap 3

WHERE vs HAVING?

```text
WHERE
→ before grouping

HAVING
→ after grouping
```

---

## Trap 4

INNER JOIN vs LEFT JOIN?

```text
INNER JOIN
→ matching rows only

LEFT JOIN
→ everything from left + matching right rows
```

---

## Trap 5

Why can JOINs duplicate data?

Because a one-to-many relationship can create multiple rows for one original record.

---

## Trap 6

How do you find missing matches?

Classic:

```sql
LEFT JOIN
WHERE right_table.id IS NULL
```

---

## Trap 7

GROUP BY vs Window Function?

```text
GROUP BY
→ collapses rows

Window function
→ retains rows
```

---

## Trap 8

ROW_NUMBER vs RANK?

```text
ROW_NUMBER
→ every row gets unique number

RANK
→ ties share rank and create gaps
```

---

## Trap 9

What is DISTINCT doing?

It removes duplicate **result rows/combinations**.

It doesn't magically remove duplicates from your underlying tables.

# 33. Advanced but Useful: UNION vs UNION ALL

`UNION` removes duplicates.

```sql
SELECT country FROM customers
UNION
SELECT country FROM suppliers;
```

`UNION ALL` keeps duplicates.

```sql
SELECT country FROM customers
UNION ALL
SELECT country FROM suppliers;
```

### Memory

```text
UNION
→ combine + deduplicate

UNION ALL
→ combine everything
```

---

# 34. Advanced: EXISTS

You may see:

```sql
SELECT *
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

This asks:

> Does at least one matching order exist?

Conceptually:

```text
EXISTS
→ Does a matching record exist?
```

---

# 35. Advanced: NULLIF

Useful for avoiding division by zero.

```sql
revenue / NULLIF(order_count, 0)
```

If `order_count = 0`, `NULLIF` returns NULL instead of zero.
