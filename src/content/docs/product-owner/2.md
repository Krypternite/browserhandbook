# SQL Concepts Explained

## EXL Product Owner Interview — Concept-First Study Guide

> **How to use this guide:** Don't memorize the queries. Understand what happens to the data at each step.
>
> The goal is to be able to look at a business question and think: **"What is the data doing here?"**

---

# 1. The Dataset We'll Use

Throughout this guide, imagine we're working with a simple e-commerce product.

## Customers

| customer_id | name | country | status |
|---:|---|---|---|
| 1 | Alice | India | Active |
| 2 | Bob | India | Active |
| 3 | Charlie | USA | Inactive |
| 4 | David | UK | Active |
| 5 | Eva | India | Active |

---

## Orders

| order_id | customer_id | order_date | amount | status |
|---:|---:|---|---:|---|
| 101 | 1 | 2026-01-05 | 500 | Completed |
| 102 | 1 | 2026-01-10 | 700 | Completed |
| 103 | 2 | 2026-01-11 | 300 | Completed |
| 104 | 2 | 2026-02-02 | 900 | Cancelled |
| 105 | 4 | 2026-02-10 | 1500 | Completed |
| 106 | 5 | 2026-02-15 | 200 | Completed |

This dataset is intentionally simple.

The important relationship is:

```text
Customers
    |
    | customer_id
    |
    ↓
Orders
```

One customer can have **many orders**.

That one fact explains a huge amount of SQL.

---

# 2. First Principle: What Does One Row Represent?

Before writing SQL, ask:

> **What does one row represent?**

This is called the **grain** of the table.

### Customers

One row = one customer.

```text
customer_id = 1
```

represents Alice.

### Orders

One row = one order.

```text
order_id = 101
```

represents one transaction.

### Why does this matter?

Suppose Alice has two orders:

```text
Alice → Order 101
Alice → Order 102
```

Alice appears twice when you look at the Orders table.

If you forget that, you can accidentally:

- double-count customers
- overstate revenue
- calculate incorrect averages
- misunderstand joins

### Interview phrase

> "Before aggregating or joining, I would first understand the grain of the tables."

That's a very good habit to develop.

---

# 3. SELECT

`SELECT` answers:

> **What columns do I want to see?**

```sql
SELECT
    name,
    country
FROM customers;
```

Result:

| name | country |
|---|---|
| Alice | India |
| Bob | India |
| Charlie | USA |
| David | UK |
| Eva | India |

You can think of it as:

```text
SELECT → columns
FROM   → table
```

---

# 4. SELECT *

```sql
SELECT *
FROM customers;
```

`*` means:

> Give me every column.

Useful when exploring a table.

Less desirable in production when you already know what columns you need.

### Why?

Because you may retrieve:

- unnecessary data
- sensitive columns
- large amounts of data
- columns you don't actually need

Prefer:

```sql
SELECT customer_id, name, country
FROM customers;
```

when you know what you need.

---

# 5. DISTINCT — What Does It Actually Do?

This is an important concept.

Suppose:

```sql
SELECT country
FROM customers;
```

Result:

| country |
|---|
| India |
| India |
| USA |
| UK |
| India |

There are five rows.

But perhaps you want to know:

> "Which countries do we have customers in?"

Use:

```sql
SELECT DISTINCT country
FROM customers;
```

Result:

| country |
|---|
| India |
| USA |
| UK |

---

## What DISTINCT actually means

`DISTINCT` removes duplicate **rows from the selected result**.

This distinction is extremely important.

Consider:

```sql
SELECT DISTINCT country, status
FROM customers;
```

SQL looks at the **combination**:

```text
country + status
```

not each column independently.

For example:

| country | status |
|---|---|
| India | Active |
| India | Inactive |
| India | Active |

After DISTINCT:

| country | status |
|---|---|
| India | Active |
| India | Inactive |

Because these are two different combinations.

---

## DISTINCT with COUNT

Very common:

```sql
SELECT COUNT(DISTINCT customer_id)
FROM orders;
```

This means:

> Count unique customers who appear in the Orders table.

This is **not** the same as:

```sql
SELECT COUNT(customer_id)
FROM orders;
```

because Alice has two orders.

### Our data

Orders contain:

```text
Alice
Alice
Bob
Bob
David
Eva
```

`COUNT(customer_id)`:

```text
6
```

`COUNT(DISTINCT customer_id)`:

```text
4
```

Because there are four unique customers:

```text
Alice
Bob
David
Eva
```

---

## Product Owner relevance

Suppose someone says:

> "We had 100,000 transactions."

That doesn't necessarily mean:

> "We had 100,000 customers."

You might need:

```sql
COUNT(DISTINCT customer_id)
```

to calculate the number of unique customers.

### Remember

```text
COUNT(*)                → rows
COUNT(column)           → non-NULL values
COUNT(DISTINCT column)  → unique non-NULL values
```

---

# 6. WHERE — Filtering Rows

Suppose you want only active customers.

```sql
SELECT *
FROM customers
WHERE status = 'Active';
```

`WHERE` filters **individual rows**.

Think:

```text
Table
  ↓
WHERE
  ↓
Only rows satisfying the condition
```

---

## Multiple conditions

```sql
SELECT *
FROM customers
WHERE country = 'India'
  AND status = 'Active';
```

Both conditions must be true.

---

## OR

```sql
SELECT *
FROM customers
WHERE country = 'India'
   OR country = 'USA';
```

At least one condition must be true.

---

## IN

Instead of:

```sql
WHERE country = 'India'
   OR country = 'USA'
   OR country = 'UK'
```

you can write:

```sql
WHERE country IN ('India', 'USA', 'UK');
```

Much cleaner.

---

## BETWEEN

```sql
SELECT *
FROM orders
WHERE amount BETWEEN 500 AND 1000;
```

Conceptually:

```text
500 ≤ amount ≤ 1000
```

---

## LIKE

Find names beginning with A:

```sql
SELECT *
FROM customers
WHERE name LIKE 'A%';
```

`%` means any sequence of characters.

```text
'A%'    → starts with A
'%a'    → ends with a
'%a%'   → contains a
```

---

# 7. ORDER BY — Ordering Your Results

`ORDER BY` answers:

> **In what order should I see the results?**

```sql
SELECT *
FROM orders
ORDER BY amount;
```

Default is generally ascending.

Largest first:

```sql
SELECT *
FROM orders
ORDER BY amount DESC;
```

Smallest first:

```sql
SELECT *
FROM orders
ORDER BY amount ASC;
```

---

## Why ORDER BY matters

Suppose the Product Owner asks:

> "Give me the top 3 customers by revenue."

You can't simply calculate revenue.

You need to:

1. Calculate revenue per customer.
2. Sort it.
3. Take the top 3.

For example:

```sql
SELECT
    customer_id,
    SUM(amount) AS total_revenue
FROM orders
GROUP BY customer_id
ORDER BY total_revenue DESC
LIMIT 3;
```

Here:

```text
GROUP BY → calculates revenue per customer
ORDER BY  → puts highest revenue first
LIMIT     → keeps top 3
```

---

# 8. ORDER BY Multiple Columns

You can sort by more than one thing.

```sql
SELECT *
FROM customers
ORDER BY country ASC, name ASC;
```

SQL first sorts by country.

If two customers have the same country, it sorts those customers by name.

---

# 9. LIMIT

```sql
SELECT *
FROM orders
ORDER BY amount DESC
LIMIT 3;
```

This means:

> Give me the first 3 rows after sorting.

Conceptually:

```text
FROM
 ↓
ORDER BY
 ↓
LIMIT
```

---

# 10. The Importance of SQL's Logical Order

This is one of the most useful concepts for understanding SQL.

You write:

```sql
SELECT
FROM
WHERE
GROUP BY
HAVING
ORDER BY
LIMIT
```

But conceptually SQL processes the query roughly like:

```text
FROM
 ↓
JOIN
 ↓
WHERE
 ↓
GROUP BY
 ↓
HAVING
 ↓
SELECT
 ↓
ORDER BY
 ↓
LIMIT
```

This explains many SQL interview questions.

# 11. Aggregation — Turning Many Rows Into Information

Aggregation answers questions like:

> How much?

> How many?

> What's the average?

> What's the maximum?

Important functions:

```sql
COUNT()
SUM()
AVG()
MIN()
MAX()
```

---

# 12. COUNT()

Count rows:

```sql
SELECT COUNT(*)
FROM orders;
```

Our table has six orders:

```text
6
```

---

## COUNT(column)

```sql
SELECT COUNT(amount)
FROM orders;
```

This counts rows where `amount` isn't NULL.

---

## COUNT(DISTINCT)

```sql
SELECT COUNT(DISTINCT customer_id)
FROM orders;
```

This answers:

> How many unique customers placed orders?

---

# 13. SUM()

`SUM()` adds numeric values.

```sql
SELECT SUM(amount) AS total_revenue
FROM orders;
```

This gives total order value.

---

## Important Product Owner question

Should cancelled orders count?

Our Orders table has:

```text
Order 104 → 900 → Cancelled
```

If the business defines revenue as completed transactions, this query is wrong:

```sql
SELECT SUM(amount)
FROM orders;
```

You need:

```sql
SELECT SUM(amount)
FROM orders
WHERE status = 'Completed';
```

### This is Product Thinking

SQL can calculate the number.

But **the Product Owner must know what the number means.**

Before writing a query, clarify the business definition.

---

# 14. AVG()

Average:

```sql
SELECT AVG(amount)
FROM orders;
```

This gives average order value.

But be careful.

If you include cancelled orders, you may calculate the wrong business metric.

```sql
SELECT AVG(amount)
FROM orders
WHERE status = 'Completed';
```

---

# 15. MIN() and MAX()

```sql
SELECT
    MIN(amount) AS smallest_order,
    MAX(amount) AS largest_order
FROM orders
WHERE status = 'Completed';
```

Useful for:

- minimum order
- maximum order
- earliest date
- latest date

---

# 16. GROUP BY — The Big Concept

Without GROUP BY:

```sql
SELECT SUM(amount)
FROM orders;
```

You get **one number**.

With:

```sql
SELECT
    customer_id,
    SUM(amount)
FROM orders
GROUP BY customer_id;
```

you get one result **per customer**.

Conceptually:

```text
All orders
    ↓
GROUP BY customer_id
    ↓
Group 1 → Alice's orders
Group 2 → Bob's orders
Group 3 → David's orders
Group 4 → Eva's orders
    ↓
SUM each group
```

---

# 17. GROUP BY Example

```sql
SELECT
    customer_id,
    SUM(amount) AS total_spend
FROM orders
WHERE status = 'Completed'
GROUP BY customer_id;
```

Result conceptually:

| customer_id | total_spend |
|---:|---:|
| 1 | 1200 |
| 2 | 300 |
| 4 | 1500 |
| 5 | 200 |

---

# 18. GROUP BY Multiple Columns

You can group by multiple dimensions.

```sql
SELECT
    country,
    status,
    COUNT(*) AS customer_count
FROM customers
GROUP BY country, status;
```

SQL groups by the **combination**:

```text
India + Active
India + Inactive
USA + Active
USA + Inactive
...
```

---

# 19. HAVING — Filtering Aggregated Results

This is one of the most common interview concepts.

Suppose:

> Find customers whose total spending is greater than ₹1,000.

You can't do:

```sql
WHERE SUM(amount) > 1000
```

because `WHERE` works before aggregation.

Instead:

```sql
SELECT
    customer_id,
    SUM(amount) AS total_spend
FROM orders
GROUP BY customer_id
HAVING SUM(amount) > 1000;
```

---

# 20. WHERE vs HAVING

Memorize this:

```text
WHERE
→ filters rows

HAVING
→ filters groups
```

Example:

```sql
SELECT
    customer_id,
    SUM(amount) AS total_spend
FROM orders
WHERE status = 'Completed'
GROUP BY customer_id
HAVING SUM(amount) > 1000;
```

Execution conceptually:

```text
Orders
 ↓
WHERE status = Completed
 ↓
GROUP BY customer
 ↓
SUM(amount)
 ↓
HAVING SUM(amount) > 1000
 ↓
Result
```

---

# 21. CASE — SQL's IF/ELSE

`CASE` lets you create logic.

Think:

```text
IF condition
    THEN result
ELSE IF condition
    THEN result
ELSE
    result
```

SQL:

```sql
CASE
    WHEN condition THEN result
    WHEN condition THEN result
    ELSE result
END
```

---

# 22. Simple CASE Example

Suppose we want to classify orders:

```sql
SELECT
    order_id,
    amount,
    CASE
        WHEN amount >= 1000 THEN 'Large'
        WHEN amount >= 500 THEN 'Medium'
        ELSE 'Small'
    END AS order_size
FROM orders;
```

Conceptually:

| amount | order_size |
|---:|---|
| 1500 | Large |
| 900 | Medium |
| 700 | Medium |
| 500 | Medium |
| 300 | Small |
| 200 | Small |

---

# 23. CASE Evaluation Order

This is important.

SQL evaluates the conditions from top to bottom.

Consider:

```sql
CASE
    WHEN amount >= 500 THEN 'Medium'
    WHEN amount >= 1000 THEN 'Large'
    ELSE 'Small'
END
```

An amount of 1500 satisfies:

```text
amount >= 500
```

first.

So it gets:

```text
Medium
```

not Large.

### Correct order:

```sql
CASE
    WHEN amount >= 1000 THEN 'Large'
    WHEN amount >= 500 THEN 'Medium'
    ELSE 'Small'
END
```

### Interview takeaway

> Put more specific/high-priority conditions before broader conditions.

---

# 24. CASE With Aggregation

You can combine CASE with COUNT.

Suppose:

> How many completed and cancelled orders do we have?

```sql
SELECT
    COUNT(CASE
        WHEN status = 'Completed'
        THEN 1
    END) AS completed_orders,

    COUNT(CASE
        WHEN status = 'Cancelled'
        THEN 1
    END) AS cancelled_orders

FROM orders;
```

---

# 25. CASE for Product Metrics

Suppose you want conversion:

```sql
SELECT
    COUNT(DISTINCT user_id) AS total_users,

    COUNT(DISTINCT CASE
        WHEN purchased = 1
        THEN user_id
    END) AS purchasing_users
FROM users;
```

Then:

```text
Conversion Rate =
Purchasing Users / Total Users
```

This pattern is extremely useful.

---

# 26. NULL — What Is It?

`NULL` does not mean:

```text
0
```

It does not mean:

```text
empty string
```

It means:

> The value is missing/unknown/not available.

---

# 27. Checking NULL

Wrong:

```sql
WHERE country = NULL
```

Correct:

```sql
WHERE country IS NULL
```

And:

```sql
WHERE country IS NOT NULL
```

---

# 28. Why NULL Is Important

Suppose a customer has no phone number.

```text
phone = NULL
```

If you calculate:

```sql
AVG()
SUM()
COUNT()
```

NULL behavior matters.

For example:

```sql
COUNT(phone)
```

doesn't count NULL phone values.

But:

```sql
COUNT(*)
```

still counts the row.

---

# 29. COALESCE

`COALESCE` gives you the first non-NULL value.

```sql
SELECT
    customer_id,
    COALESCE(phone, 'Not Available') AS phone
FROM customers;
```

Think:

```text
COALESCE(A, B)

If A exists → use A
Otherwise   → use B
```

Another example:

```sql
COALESCE(discount, 0)
```

means:

> If discount is NULL, treat it as zero.

---

# 30. JOINS — Why They Matter

Real business data is rarely in one table.

You might have:

```text
Customers
Orders
Products
Payments
Events
Subscriptions
```

To answer business questions, you need to combine them.

That's why JOINs are so important.

---

# 31. INNER JOIN

```sql
SELECT
    c.name,
    o.order_id,
    o.amount
FROM customers c
INNER JOIN orders o
    ON c.customer_id = o.customer_id;
```

Only matching customers and orders appear.

Conceptually:

```text
Customers     Orders

Alice    ───── Order 101
Alice    ───── Order 102
Bob      ───── Order 103
Charlie  ───── nothing
David    ───── Order 105
Eva      ───── Order 106
```

Charlie disappears.

---

# 32. LEFT JOIN

```sql
SELECT
    c.name,
    o.order_id,
    o.amount
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id;
```

Every customer remains.

Charlie gets NULL values for order columns.

This is incredibly useful.

---

# 33. The Classic "Never Did Something" Pattern

Question:

> Find customers who never placed an order.

```sql
SELECT
    c.customer_id,
    c.name
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
```

The logic is:

```text
Keep every customer
        ↓
Try to find their order
        ↓
If no order exists → order_id = NULL
        ↓
Keep those rows
```

This pattern is worth memorizing.

---

# 34. Why JOINs Can Create Duplicates

Alice has:

```text
Order 101
Order 102
```

Therefore, after joining:

```text
Alice | 101
Alice | 102
```

Alice appears twice.

That's not necessarily a duplicate.

It's because the relationship is:

```text
1 customer
    ↓
many orders
```

This is called a **one-to-many relationship**.

---

# 35. The Dangerous Revenue Join

Imagine:

### Orders

```text
order_id | amount
---------|-------
1        | 100
```

### Order Items

```text
order_id | product
---------|--------
1        | A
1        | B
```

Joining them produces:

```text
1 | 100 | A
1 | 100 | B
```

Now:

```sql
SUM(amount)
```

could incorrectly become:

```text
200
```

instead of:

```text
100
```

### Why?

Because the order amount was repeated for each item.

### Lesson

> **Always understand table grain before aggregating after a JOIN.**

This is one of the most valuable SQL concepts for you.

---

# 36. Subqueries

A subquery is a query inside another query.

Example:

> Find employees earning more than the average salary.

```sql
SELECT *
FROM employees
WHERE salary > (
    SELECT AVG(salary)
    FROM employees
);
```

Inner query:

```sql
SELECT AVG(salary)
FROM employees;
```

calculates the average.

Outer query compares each employee against it.

Think:

```text
Inner query
    ↓
produces a value/result
    ↓
Outer query uses it
```

---

# 37. CTEs

CTE means:

> Common Table Expression.

Syntax:

```sql
WITH customer_sales AS (
    SELECT
        customer_id,
        SUM(amount) AS total_sales
    FROM orders
    GROUP BY customer_id
)

SELECT *
FROM customer_sales
WHERE total_sales > 1000;
```

Think of it as:

> "First, create this temporary logical result. Then use it."

---

# 38. Why CTEs Are Useful

Without a CTE, a complicated query can become difficult to understand.

CTE:

```text
Step 1 → calculate customer revenue
Step 2 → filter high-value customers
Step 3 → calculate ranking
Step 4 → final result
```

This makes analytical SQL easier to reason about.

---

# 39. Window Functions

Window functions are different from GROUP BY.

### GROUP BY

Collapses rows.

### Window function

Calculates across related rows **without collapsing them**.

This distinction is extremely important.

---

# 40. GROUP BY vs Window Function

Suppose:

```text
Customer | Order
---------|------
Alice    | 500
Alice    | 700
Bob      | 300
```

With GROUP BY:

```sql
SELECT
    customer_id,
    SUM(amount)
FROM orders
GROUP BY customer_id;
```

Result:

```text
Alice | 1200
Bob   | 300
```

Original order rows are gone.

---

With a window function:

```sql
SELECT
    customer_id,
    amount,
    SUM(amount) OVER (
        PARTITION BY customer_id
    ) AS customer_total
FROM orders;
```

Result:

```text
Alice | 500 | 1200
Alice | 700 | 1200
Bob   | 300 | 300
```

The original rows remain.

### Remember

```text
GROUP BY
→ collapses rows

WINDOW FUNCTION
→ keeps rows
```

---

# 41. PARTITION BY

`PARTITION BY` defines the group over which the window function operates.

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
)
```

means:

> Calculate the sum separately for each customer.

---

# 42. ROW_NUMBER()

Suppose Alice has three orders.

```sql
SELECT
    customer_id,
    order_id,
    order_date,

    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY order_date DESC
    ) AS rn

FROM orders;
```

For Alice:

```text
Order 102 → 1
Order 101 → 2
```

because newest order comes first.

---

# 43. Finding the Latest Order

Now filter:

```sql
WITH ranked_orders AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY order_date DESC
        ) AS rn
    FROM orders
)

SELECT *
FROM ranked_orders
WHERE rn = 1;
```

Mental model:

```text
Group by customer
       ↓
Sort newest first
       ↓
Number rows
       ↓
Take row #1
```

This is a **must-know interview pattern**.

---

# 44. RANK()

Suppose scores:

```text
100
90
90
80
```

Using:

```sql
RANK() OVER (
    ORDER BY score DESC
)
```

produces:

```text
100 → 1
90  → 2
90  → 2
80  → 4
```

---

# 45. DENSE_RANK()

```sql
DENSE_RANK() OVER (
    ORDER BY score DESC
)
```

produces:

```text
100 → 1
90  → 2
90  → 2
80  → 3
```

### Memory trick

```text
RANK
→ leaves gaps

DENSE_RANK
→ no gaps
```

---

# 46. ROW_NUMBER vs RANK vs DENSE_RANK

| Function | Ties share rank? | Gaps? |
|---|---|---|
| ROW_NUMBER | No | No |
| RANK | Yes | Yes |
| DENSE_RANK | Yes | No |

---

# 47. Top 3 Products Per Category

This is a classic SQL problem.

```sql
WITH ranked_products AS (
    SELECT
        category,
        product_id,
        revenue,

        DENSE_RANK() OVER (
            PARTITION BY category
            ORDER BY revenue DESC
        ) AS rnk

    FROM product_sales
)

SELECT *
FROM ranked_products
WHERE rnk <= 3;
```

Important:

```text
PARTITION BY category
```

means:

> Start the ranking again for every category.

---

# 48. LAG()

`LAG()` lets you see the previous row.

Suppose:

| month | revenue |
|---|---:|
| Jan | 100 |
| Feb | 120 |
| Mar | 150 |

```sql
SELECT
    month,
    revenue,

    LAG(revenue) OVER (
        ORDER BY month
    ) AS previous_revenue

FROM monthly_revenue;
```

Result:

| month | revenue | previous_revenue |
|---|---:|---:|
| Jan | 100 | NULL |
| Feb | 120 | 100 |
| Mar | 150 | 120 |

---

# 49. Why LAG Is Useful

Now we can calculate:

```text
Month-over-month growth
```

Conceptually:

```text
Current Revenue - Previous Revenue
----------------------------------
Previous Revenue
```

For February:

```text
(120 - 100) / 100
= 20%
```

This is very relevant to Product Analytics.

---

# 50. LEAD()

`LEAD()` looks forward.

```sql
LEAD(revenue) OVER (
    ORDER BY month
)
```

Memory:

```text
LAG
→ look backward

LEAD
→ look forward
```

# 51. Product Analytics — Why SQL Matters for a PO

This is where you should connect everything.

A Product Owner might ask:

> How many users are active?

SQL gives you the answer.

But the PO needs to define:

> What counts as active?

That is a **product definition**, not merely an SQL problem.

---

# 52. DAU

DAU = Daily Active Users.

Usually:

```text
Unique users
who performed a defined meaningful action
during a day.
```

SQL concept:

```sql
COUNT(DISTINCT user_id)
```

combined with a date filter.

---

# 53. MAU

MAU = Monthly Active Users.

Again:

```sql
COUNT(DISTINCT user_id)
```

but for the defined monthly period.

---

# 54. Conversion Rate

Example funnel:

```text
1000 signed up
800 started onboarding
600 completed onboarding
300 purchased
```

Signup → purchase conversion:

```text
300 / 1000 = 30%
```

But a good PO should ask:

> What exactly counts as a signup?

> What counts as a completed purchase?

> Are cancelled purchases excluded?

---

# 55. Feature Adoption

Suppose 10,000 eligible users exist.

2,500 used Feature X.

```text
Feature Adoption =
2500 / 10000
= 25%
```

SQL can calculate the numerator.

Product thinking defines the denominator.

That distinction is important.

---

# 56. Retention

Retention asks:

> Do users continue to come back?

For example:

```text
1000 users signed up
300 returned the following month
```

Retention:

```text
30%
```

Again, SQL measures it.

The PO defines:

- what "returned" means
- which cohort we're measuring
- the time window
- whether certain users should be excluded

# 57. Churn

Churn usually means users/customers becoming inactive.

But **never assume the definition**.

A strong PO response is:

> "I would first clarify the business definition of churn—for example, no completed transaction for 90 days—before building the metric."

Then SQL can identify those customers.

# 59. COUNT vs SUM vs AVG — Product Interpretation

# 61. Common SQL Mistakes

## Mistake 1 — Using `=` with NULL

Wrong:

```sql
WHERE phone = NULL
```

Correct:

```sql
WHERE phone IS NULL
```

---

## Mistake 2 — Using WHERE Instead of HAVING

Wrong:

```sql
WHERE SUM(amount) > 1000
```

Correct:

```sql
HAVING SUM(amount) > 1000
```

---

## Mistake 3 — Forgetting DISTINCT

Wrong for unique users:

```sql
COUNT(user_id)
```

Potentially correct:

```sql
COUNT(DISTINCT user_id)
```

---

## Mistake 4 — Wrong JOIN

If you need customers who never ordered:

Don't use only:

```sql
INNER JOIN
```

because that removes customers with no orders.

Use:

```sql
LEFT JOIN
```

then:

```sql
WHERE order_id IS NULL
```

---

## Mistake 5 — Double Counting After JOIN

Always ask:

> What is the grain after this JOIN?

---

## Mistake 6 — Incorrect CASE ordering

Wrong:

```sql
CASE
    WHEN amount >= 500 THEN 'Medium'
    WHEN amount >= 1000 THEN 'Large'
END
```

Correct:

```sql
CASE
    WHEN amount >= 1000 THEN 'Large'
    WHEN amount >= 500 THEN 'Medium'
END
```

---

## Mistake 7 — Confusing GROUP BY and Window Functions

Remember:

```text
GROUP BY
→ reduces rows

Window function
→ keeps rows
```

# 62. A Practical Query-Building Method

When the interviewer gives you a problem, don't immediately type.

Take 10–15 seconds.

Ask yourself:

### Step 1 — What is the output?

Example:

> "I need customer ID and total revenue."

### Step 2 — Where does the data live?

```text
customer_id → Orders
amount      → Orders
```

### Step 3 — What is the grain?

```text
One row = one order
```

### Step 4 — Do I need a JOIN?

If customer information is needed:

```text
Yes
```

### Step 5 — Do I need filtering?

Completed orders only?

```text
WHERE status = 'Completed'
```

### Step 6 — Do I need aggregation?

Revenue per customer?

```text
SUM(amount)
GROUP BY customer_id
```

### Step 7 — Do I need ranking?

Top 3?

```text
RANK / DENSE_RANK / ROW_NUMBER
```

This approach will make you much calmer in an interview.

# 63. A Full Example

### Business request

> "Find the top 3 customers by completed-order revenue in each country."

Break it down.

### Tables

```text
Customers
Orders
```

### Relationship

```text
customer_id
```

### Filter

```text
status = Completed
```

### Aggregation

```text
SUM(amount)
```

### Grouping

```text
country + customer
```

### Ranking

```text
Top 3 per country
```

Query:

```sql
WITH customer_revenue AS (
    SELECT
        c.country,
        c.customer_id,
        c.name,
        SUM(o.amount) AS revenue

    FROM customers c

    JOIN orders o
        ON c.customer_id = o.customer_id

    WHERE o.status = 'Completed'

    GROUP BY
        c.country,
        c.customer_id,
        c.name
),

ranked_customers AS (
    SELECT
        *,
        DENSE_RANK() OVER (
            PARTITION BY country
            ORDER BY revenue DESC
        ) AS rnk

    FROM customer_revenue
)

SELECT
    country,
    customer_id,
    name,
    revenue
FROM ranked_customers
WHERE rnk <= 3;
```

Don't memorize this query.

Understand the pipeline:

```text
Customers + Orders
       ↓
JOIN
       ↓
Completed orders
       ↓
Revenue per customer
       ↓
Rank within country
       ↓
Top 3
```
